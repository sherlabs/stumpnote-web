# 01 Architecture

Index: [README.md](./README.md). Decisions referenced as D-xx live in [00-overview.md](./00-overview.md) section 7. Executed mainly in S1 ([brief](../ops/stages/S1-scaffold.md)) and S6 ([brief](../ops/stages/S6-admin-analytics.md)).

## 1. Shape

One Next.js App Router application with Payload CMS embedded. The marketing site, the Payload admin and the Payload REST/GraphQL API ship as one Vercel project (`stumpnote-site`). Public pages are statically generated or ISR; only `/admin` and `/api` touch the database at request time.

```
Browser ──► Vercel CDN ──► Next.js (Fluid compute)
                            ├─ (site)      static / ISR pages, no DB at request time
                            ├─ (payload)   /admin UI, /api/* REST, /api/graphql
                            │                └─ Payload Local API ──► Neon Postgres (pooled)
                            ├─ analytics views (server components, admin role only)
                            │     ├─► web analytics provider API (PostHog HogQL or Plausible Stats; server key)
                            │     └─► StumpNote Supabase, read-only role, analytics schema
                            └─ Vercel Blob (media)
```

Versions (D-02): Payload >= 3.90.2 (all `@payloadcms/*` identical), Next inside `@payloadcms/next` peer range (16.3.x at time of writing), React 19.3, Node `24.x` (`engines.node`), pnpm 10 (`packageManager`), Tailwind 4, TypeScript as the template ships. Base: Payload template `with-vercel-website` (plugins: form-builder, nested-docs, redirects, search, seo; Live Preview; drafts; Header/Footer globals). Bump its dependency versions on first install; re-check the Next peer range when bumping.

## 3. Environments

| Env | URL | DB | Media | Analytics | Notes |
|---|---|---|---|---|---|
| local | `http://localhost:3000` | Docker `postgres:17-alpine` (`pnpm db:up`) | local filesystem (`media/`, gitignored) when `BLOB_READ_WRITE_TOKEN` unset | `ANALYTICS_MODE=fixtures` | Payload **push mode** allowed locally only on a throwaway DB; before committing a migration, run `payload migrate:create` against a fresh local DB |
| preview | `*.vercel.app` per branch, Vercel Authentication on | Neon **branch** (never prod) or `DATABASE_URI` unset for DB-free skeleton | Blob (same store, `preview/` prefix) or disabled | fixtures | Previews must not hold production credentials |
| production | `stumpnote.com` (after S7), `stumpnote-site.vercel.app` before | Neon main branch, pooled URL | Blob | live keys | Migrations run in the build step with the unpooled URL |

**DB-free build is a hard requirement for S1.** `next build` must succeed with `DATABASE_URI` unset: no Payload queries in `generateStaticParams` or page bodies at build time until the DB exists (guard with `if (!process.env.DATABASE_URI) return []`), admin routes are dynamic by nature, and the build command is `pnpm build` (not `payload migrate && pnpm build`) until the DB is provisioned; then switch to `pnpm ci` (`payload migrate && payload build`). This lets the skeleton deploy before the Neon gate is cleared.

## 4. Database and migrations (D-03, D-04)

- Adapter: `@payloadcms/db-postgres`, `pool: { connectionString: process.env.DATABASE_URI, max: 1 }`, `push: process.env.NODE_ENV === 'development' && process.env.PAYLOAD_PUSH === 'true'`. Push is opt-in even locally so nobody accidentally mixes push and migrations.
- Migrations: `pnpm payload migrate:create <name>` locally against a fresh Docker DB, commit the generated files under `migrations/`, `pnpm payload migrate` runs in `ci`. Never `prodMigrations` (slows cold starts).
- Neon: pooled URL (`-pooler` host) for runtime; direct URL for migrations (`DATABASE_URI_UNPOOLED`). Build command once DB exists: `DATABASE_URI=$DATABASE_URI_UNPOOLED pnpm ci` set as Vercel build command, or read the unpooled var inside `payload.config.ts` when `process.env.PAYLOAD_MIGRATING === 'true'`. Test on the first real deploy; record which worked in `decisions.md`.
- Free-plan facts to design around: scale-to-zero after 5 min (first admin load slow), 100 compute-hours/month, 1 GB storage. Builds wake the DB; skip docs-only builds with `vercel.json` `ignoreCommand: "git diff --quiet ${VERCEL_GIT_PREVIOUS_SHA:-HEAD^} HEAD -- . ':!docs' ':!*.md'"` (exit 0 = skip, non-zero = build). Do NOT use plain `HEAD^ HEAD`: a push of two commits (code, then docs) would compare only the docs commit and silently skip the production build. `VERCEL_GIT_PREVIOUS_SHA` (last successfully deployed commit of the branch) is provided to the Ignored Build Step; if it is empty or not in the shallow clone the command errors or falls back and the build runs, which is the safe direction. Verify behaviour on the first two-commit push and record it in `decisions.md`.
- Backups: Neon point-in-time restore (short window on free). Before any destructive migration run `pg_dump` locally (`scripts/db-dump.sh`, output gitignored).
- Local reset: `pnpm db:reset` drops and recreates the Docker volume then runs migrations and seed.

## 6. Media (D-05)

`@payloadcms/storage-vercel-blob` with `clientUploads: true` (bypasses the 4.5 MB function body limit), `addRandomSuffix: true`. `Media` collection `imageSizes`: `thumb` (400), `card` (800), `hero` (1600), all WebP, `sharp` on the server. `next.config` `images.unoptimized = true` for `/public` assets (SVG mark, fonts, OG) and `remotePatterns` for the Blob host for CMS images. Hobby/Pro image-transformation quotas are therefore mostly untouched. Enforce a 10 MB upload cap and `mimeTypes: ['image/*', 'video/mp4']` in the collection.

## 7. Caching

- Public pages: `export const revalidate = 3600` (ISR) or fully static. On publish, a Payload `afterChange` hook calls `revalidatePath`/`revalidateTag` for the affected routes (template pattern).
- Payload reads inside server components use `unstable_cache` keyed by collection + slug + `_status`.
- Analytics: `src/analytics/cache.ts` wraps provider calls with `unstable_cache` TTLs: web analytics 5 min, AI spend 10 min, product 15 min, RevenueCat 30 min. Fixtures are not cached.
- Response headers: public pages `Cache-Control: public, s-maxage=3600, stale-while-revalidate=86400`; `/admin` and `/api` `no-store`.
- Fonts: self-hosted woff2 with `Cache-Control: immutable` (Vercel default for hashed assets).

## 8. Security model

### 8.1 Admin authentication and roles (D-08)
- `Users` collection: `auth: { tokenExpiration: 7200, maxLoginAttempts: 5, lockTime: 15 * 60 * 1000, cookies: { secure: true, sameSite: 'Strict' } }`.
- `roles: select hasMany [admin, editor, viewer]`, default `viewer`, field-level `update` access `isAdmin`.
- Access helpers: `isAdmin`, `isEditor` (admin or editor), `isAdminOrSelf`, `publishedOnly` (read `_status: published` for anonymous).
- Collections: create/update/delete = `isEditor`; delete on LegalPages = `isAdmin`; Users = `isAdmin` (self can update own name/password); globals SiteSettings/LegalValues/AnalyticsSettings = `isAdmin`.
- First-user flow: Payload opens registration until the first user exists. **Gap fixed in spec review:** with `roles` defaulting to `viewer` and field-level update restricted to admins, the first account would be created without any admin role and nobody could ever grant it (lockout). `Users` therefore needs a `beforeValidate`/`beforeChange` hook (operation `create`): if the `users` collection is empty (`payload.count` = 0), force `roles = ['admin']`; otherwise strip any client-supplied `roles` unless the requester is an admin. Unit-test both branches. After that, `Users.access.create = isAdmin` closes registration (the Payload create-first-user screen only shows while the collection is empty, and the access function is only consulted once users exist; verify this in S1-12 and record in `decisions.md`).
- MFA: optional `payload-totp` (version compatible with Payload 3.90+), enabled in S6 if the user wants it; recorded in `decisions.md`.
- Custom admin views are public by default in Payload: every view component checks `initPageResult.req.user?.roles?.includes('admin')` and returns `notFound()` otherwise. A Playwright test asserts `/admin/analytics/web` returns 404/redirect when logged out.
- No custom REST endpoints for analytics (views read `searchParams` directly). If one is ever added, wrap with the same role check and add a 401 test.

### 8.2 Audit and throttling
- `AuditLog` collection (admin read-only in UI): `user`, `action` (`login`, `view:web`, `view:ai-spend`, `view:product`, `publish:<collection>`), `range`, `ip`, `userAgent`, `createdAt`. Written from the view code and `afterLogin`/`afterChange` hooks. Prune rows older than 180 days from a manual admin action (no cron).
- Throttle analytics views by counting the user's audit rows in the last 60 s; above 30, render a "slow down" message instead of querying.

### 8.3 Headers and CSP
Set in `next.config` `headers()`:
```
X-Content-Type-Options: nosniff
Referrer-Policy: strict-origin-when-cross-origin
Permissions-Policy: camera=(), microphone=(), geolocation=(), interest-cohort=()
Strict-Transport-Security: max-age=31536000      (no includeSubDomains, no preload until all subdomains verified)
X-Frame-Options: SAMEORIGIN
```
CSP, two policies, start as `Content-Security-Policy-Report-Only` and switch to enforcing in S7 once clean. **Do not use a per-request nonce for the site policy**: Next.js nonces require every page to render dynamically per request, which would defeat static/ISR pages, the CDN and the performance budget. Use `script-src 'self' 'unsafe-inline'` for the public site at first (Next inline bootstrap scripts), and evaluate hash-based CSP via `experimental.sri` (Next) in S7; whichever is chosen, record the outcome and the remaining `unsafe-inline` exposure in `decisions.md`. The site has no user-generated HTML, no third-party scripts except one analytics snippet, and no raw HTML in legal rendering, so the residual XSS risk is low.
- Site: `default-src 'self'; script-src 'self' 'unsafe-inline'; style-src 'self' 'unsafe-inline'; img-src 'self' data: blob: https://*.public.blob.vercel-storage.com; font-src 'self'; connect-src 'self' <configured web-analytics ingest host, e.g. https://eu.i.posthog.com or https://plausible.io>; frame-ancestors 'none'; base-uri 'self'; form-action 'self'; object-src 'none'`.
- Admin (`/admin`, `/api`, `/next/preview`): same but `frame-ancestors 'self'` (Live Preview) and whatever inline/eval allowances Payload's admin empirically needs (test and record in `decisions.md`).
- `X-Robots-Tag: noindex, nofollow` on `/admin`, `/api`, `/lab`; `robots.ts` disallows the same.

### 8.4 Rate limiting and WAF
- Vercel WAF custom rules (dashboard, user applies in S7): rate-limit `/api/users/login` and `/api/waitlist-signups`; optional IP allow-list on `/admin`.
- Waitlist form: server action with honeypot field, per-IP in-memory token bucket (best effort on serverless), and `Turnstile`-free (no third-party widget; keep it dependency-free).

### 8.5 Repo and supply chain
- `scripts/check-secrets.sh` (gitleaks if installed, else regex) runs in `pnpm check`. GitHub secret scanning + push protection enabled in S7 ([07-deploy-runbook.md](./07-deploy-runbook.md) section 7).
- No third-party Payload analytics plugin (D-06). Dependencies pinned; `pnpm audit` in `pnpm check`.

## 9. Read-only StumpNote analytics access (D-07)

Goal: the admin shows AI spend and product usage from the StumpNote production database without ever holding a privileged credential or seeing a row about an individual.

Design:
1. **Private repo migration** (draft: [supabase-analytics-views.sql](./supabase-analytics-views.sql)) creates schema `analytics`, aggregate-only views and functions, and a `NOLOGIN` role `payload_analytics_ro`. Views are owned by `postgres` and run with owner privileges (default view semantics, deliberately not `security_invoker`) so the role never needs grants on base tables. Functions are `SECURITY DEFINER` with `search_path` pinned. Internal helper views (`_activity_user_day`, `_feature_events`) and the `config`/`excluded_subject` tables are not granted to the role. The schema is never added to PostgREST's exposed schemas.
2. **Out-of-band user steps:** `alter role payload_analytics_ro login password '<generated>'` in the Supabase SQL editor; compose the pooler URL (transaction mode, port 6543, username `payload_analytics_ro.<project-ref>`, `sslmode=require`); store it as `STUMPNOTE_ANALYTICS_DATABASE_URL` in Vercel env (Production only).
3. **Site side:** `src/analytics/stumpnote-db.ts` creates a `pg` Pool (`max: 2`, TLS with certificate verification: pass the provider's public CA certificate via `ssl: { ca }`; never set `rejectUnauthorized: false` silently, and if the pooler chain cannot be verified record the exception in `decisions.md`; `statement_timeout: 8000`) and exposes typed functions with fixed SQL strings (parameters only for day ranges and limits, clamped). No user-supplied SQL. Called only from admin server components behind the admin role check, through `cache.ts`.
4. **Fixtures:** `src/analytics/fixtures/*.json` hold synthetic rows shaped exactly like the views; `ANALYTICS_MODE=fixtures` (default) serves them so S6 ships and tests pass before any credential exists. Fixture numbers are invented and labelled "Sample data" in the UI.
5. **k-anonymity:** any breakdown that could describe a small group hides cells below `analytics.config.k_min` (default 5). Changing it is a reviewed SQL change in the private repo, not a site setting.
6. **Phase 2 upgrade (optional):** replace the direct role with a Supabase Edge Function gateway that signs requests (HMAC) and returns whitelisted JSON, so the site holds no DB credential.

Applying the migration to production is a user-approved step in S6; the S6 brief says how the private-repo PR is prepared (fresh clone, never the read-only working tree).
